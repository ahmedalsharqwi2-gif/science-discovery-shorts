# تشغيل المستودعات خارج GitHub Actions

هذه حزمة تشغيل قابلة للنقل إلى **سيرفر Linux دائم**. لم يتم توفير سيرفر أو ربط مفاتيح على هذه البيئة، ولم يُفعّل نشر عام. Android وسيلة تحكم عبر SSH؛ الرندر يعمل على السيرفر. وجود الهاتف مفتوحًا وحده لا يشغّل هذه الحزمة.

راجع [خيار Oracle المجاني أولًا](ORACLE_FREE_FIRST.md) قبل اختيار المعمارية؛ A1 يحتاج اختبار ARM، وE2.micro المجاني الصغير لا يناسب الرندر.

## المتطلبات الفعلية

- حساب سحابي وسيرفر Ubuntu 24.04 **x86_64**، يفضّل 4 أنوية و8 GB RAM و60 GB مساحة كبداية. الأداء والتكلفة يتوقفان على المزود؛ اختبر فيلمًا كاملًا قبل اعتماد الإنتاج اليومي. Oracle المجاني خيار محتمل فقط؛ السعة والتسجيل غير مضمونين، وARM يحتاج اختبار تبعيات مستقل.
- دومين فرعي مثل `media.example.com` يشير إلى عنوان السيرفر، وHTTPS عبر Caddy، وفتح 80/443. لا تضع ملفات المفاتيح أو المستودعات داخل public.
- مفاتيح Gemini وBuffer تُربط بأمان على السيرفر. **قيم GitHub Secrets القديمة لا يمكن استخراجها**؛ استخدم النسخ المحفوظة لديك أو أنشئ بدائل لدى المزود. لا ترسلها في الدردشة.
- نسخة من فرع المستودعات الذي يحتوي `professional_motion/merge_chunks.py` والسياسات الجديدة. لا تفترض أن main القديم يحتوي التحديثات قبل دمجها.

## تثبيت واضح للمسؤول عن السيرفر

1. أنشئ المستخدم `video-factory` بدون صلاحيات sudo، والمجلدات `/srv/video-factory/{repos,runtime,public}` بملكيته. يجب أن يكون `/srv/video-factory` و`public` بصلاحيات 755 لقراءة Caddy، و`runtime` بصلاحيات 700.
2. ثبّت `python3-venv`, `python3-dev`, `build-essential`, `ffmpeg`, `chromium`, `git`, Node.js 22 وCaddy من مصادر النظام الموثوقة. لا تحتاج إلى GitHub Actions أو GitHub runner أو PAT لرفع الفيديوهات؛ المستودعات العامة تُنسخ بالقراءة فقط.
3. انسخ الحزمة إلى `/opt/video-factory` (ملكية root للشفرة)، وأنشئ `/srv/video-factory/venv`. انسخ المستودعات الأربعة داخل `repos`، وثبّت requirements الخاصة بكل منها في البيئة؛ إذا ظهر تعارض تبعيات، استخدم بيئة منفصلة لكل مشروع وعدّل runner قبل التشغيل بدل تجاهله. نفّذ `npm ci` داخل `professional_motion` لكل مستودع. اختبر نسخة Chromium ومكتبات ASR على الجهاز الحقيقي.
4. انسخ `config.example.json` إلى `/etc/video-factory/config.json`، وعدّل الدومين والمسارات. انسخ مثال المفاتيح أربع مرات بالأسماء `science.json`, `horror.json`, `history.json`, `news.json`، وحدّثها داخل محرر آمن. ملكيتها `video-factory` وصلاحياتها **600**. مجلد `/etc/video-factory` بصلاحيات 750 ومجموعة `video-factory`. لا تضع مفاتيح داخل git.
5. أضف كتلة `Caddyfile.example` إلى إعداد Caddy بعد تعديل الدومين. الملفات الوحيدة المنشورة هي MP4 ذات أسماء مشتقة من SHA؛ السجلات والأصوات والأسرار لا تُخدم عبر الويب.
6. نفّذ الفحص كمستخدم الخدمة:

```bash
sudo -u video-factory /srv/video-factory/venv/bin/python /opt/video-factory/runner.py --config /etc/video-factory/config.json health
```

7. من داخل كل مستودع، نفّذ `/srv/video-factory/venv/bin/python /opt/video-factory/preflight.py` للتأكد من imports وChromium/WebGL2 بدون أي استدعاء مدفوع. runner يعيد هذا الفحص قبل الكتابة والصوت. هذا يثبت تحميل التبعيات فقط، وليس تنزيل موديلات ASR أو نجاح فيلم كامل.

شغّل **مراجعة واحدة فقط** أولًا؛ يستعمل هذا مفاتيحك وحصص API لكنه لا ينشر:

```bash
sudo -u video-factory /srv/video-factory/venv/bin/python /opt/video-factory/runner.py --config /etc/video-factory/config.json run --mode review --profiles science
```

الفيديو النهائي في `repos/<repository>/professional_motion/output/professional-review.mp4`. لتكملة مراجعة متوقفة استخدم الأمر نفسه مع `--resume`. لا تستخدم الأمر بدون resume لإعادة المحاولة: سينشئ مراجعة جديدة.

8. بعد مراجعة الأفلام وتفعيل موافقات النشر الخاصة بكل مستودع، انسخ وحدتي systemd إلى `/etc/systemd/system/` ونفّذ `systemctl daemon-reload` ثم `systemctl enable --now video-factory.timer`. **لا تفعّل المؤقت قبل اختبار الحزمة وربط المفاتيح واعتماد الفيديوهات.** الموافقات الحالية في المستودعات تبقى لازمة، فلا تتجاوزها الحزمة.

المؤقت يبدأ الإنتاج **09:00 بتوقيت القاهرة** لترك وقت للرندر، وتظل جدولة Buffer المستهدفة **17:00 بتوقيت القاهرة**، مع احتساب التوقيت الصيفي. لا يتأثر النشر بإغلاق الهاتف بعد قبول Buffer للجدولة. المؤقت الفائت يمكن أن يبدأ بعد الإقلاع، لكن runner يرفض بدء دفعة جديدة بعد 12 ظهرًا. فوات موعد النشر أو فشل الجودة يتوقف دون نشر متأخر عشوائي. لا توجد إعادة محاولة دورية مدفوعة بلا حد.

## التحكم من Android

ثبّت Termux من مصدره الرسمي/F-Droid، وثبّت `openssh` داخله، وأنشئ مفتاح SSH بقفل. أضف **المفتاح العام فقط** إلى حساب إداري محدود على السيرفر. ثم:

```bash
ssh USER@SERVER
systemctl status video-factory.timer
journalctl -u video-factory.service -n 40 --no-pager
```

لا تستخدم الهاتف لحفظ مفاتيح الخدمات في أوامر shell أو تشغيل Chromium/ASR طوال اليوم. لعرض مراجعة، انسخ MP4 عبر تطبيق SFTP آمن أو نزّله بـ`scp`؛ لا تجعل مجلد runtime عامًا. قد تحتاج صلاحيات journal ضمن مجموعة محدودة يضبطها مسؤول السيرفر.

## الأمان والاستئناف والحدود

- كل مشروع له قفل، وسجل مراحل مستقل، وأرشيف للملفات السابقة، وتُحفظ السجلات بصلاحيات خاصة. لا تشغّل workflow آخر بالتوازي على نفس النسخة.
- إذا انقطع التشغيل أثناء الإرسال إلى المزود، يتوقف الاستئناف بحالة `PublicationReconciliationRequired` بدل تكرار الطلب آليًا. راجع إيصالات المستودع ولوحة Buffer لكل وجهة قبل أي إجراء؛ لا تمسح journal لتجاوز الحالة.
- تحتفظ المستودعات بتاريخ الموضوعات وإيصالات النشر محليًا. اعمل نسخة احتياطية مشفرة يومية من state/runtime والمفاتيح منفصلة. لا تحدّث git فوق تغييرات الحالة؛ انسخها احتياطيًا وأوقف المؤقت أولًا. الحزمة لا تدفع تغييرات git تلقائيًا.
- الحزمة تحتاج ربطًا واختبارًا على المضيف الحقيقي؛ نجاح اختبارات المحاكاة المحلية ليس إثبات نشر حي أو ضمان مدة الرندر. الأصول العامة تحتاج تنظيفًا يدويًا فقط بعد التأكد من اكتمال النشر والاحتفاظ بالنسخ المطلوبة.
